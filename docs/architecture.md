# 架构与设计取舍

这份文档记录**为什么这样写**，不是「写了什么」。想知道某个函数做什么，直接读源码，那里注释更细。

---

## 三层，三种知识

| 层 | 语言 | 只懂 | 不知道 |
|---|---|---|---|
| 控制面板 `client.js` | JS（浏览器） | 渲染、轮询、把用户点击变成一次 `/api` 请求 | AutoCAD、Python、进程 |
| 插件宿主 `index.js` | JS（Node） | 进程生命周期、配置持久化、日志环形缓冲 | AutoCAD 的对象模型 |
| 桥 `bridge/*.py` | Python | COM、AutoCAD、MCP 协议 | DSH 的存在 |

拆成三层的理由不是「架构好看」，是**调试成本**。桥出问题时可以直接 `python autocad_server.py` 跑，不开 DSH、不开浏览器；面板出问题时可以只改 JS，桥进程照常跑着。如果把三者糊在一起，任何一处出问题都要启动整个 DSH 才能复现。

界面与宿主的通信只有一条通道：`/api/autocad-bridge` 这一个精确 Fetch 路由，`action` 字段区分操作。没有 WebSocket，没有事件总线。状态靠面板每 2.5 秒轮询一次 `status`、每 1.2 秒拉一次增量日志（用递增的 `seq` 游标）。轮询看起来笨，但它让「面板打开前的历史状态」和「面板打开后的实时状态」用同一套代码，省掉一整类同步 bug。

## 单 STA 线程 + 命令队列

这是整个项目里**唯一一个真正的设计决策**，其余都是工程量。

### 问题

MCP 的每次 `tools/call` 落在**随机的工作线程**上。而 COM 的 `CoInitialize` 是**按线程**的，不是按进程的。第一版用了一个布尔量记「我初始化过了」，于是：

```
线程 A: CoInitialize → 连接 CAD → 成功
线程 B: 以为已初始化 → 直接调用 → (-2147221008, '尚未调用 CoInitialize')
```

### 为什么「每个线程各初始化一次」不够

即使每个线程都 `CoInitialize`，从线程 B 去用线程 A 创建的 COM 指针，仍然是**跨套间的未 marshal 引用**。它不一定立刻报错，而是会在某个随机时刻抛 `RPC_E_WRONG_THREAD` 或者干脆崩掉进程。再叠加 AutoCAD 本身是单线程的、并发调用会互相踩（`RPC_E_CALL_REJECTED`），得到的是一个「偶发、难复现、看起来像玄学」的故障集合。

### 方案

一个常驻线程做 STA，所有 COM 调用排队进去：

```python
def _on_com(self, fn):
    if self._worker.ident == threading.get_ident():
        return fn()                      # 防止自己等自己
    return self._worker.submit(fn, timeout_s=...)
```

代价是**没有任何并行**。但 AutoCAD 本来就是串行的——并行的收益本来就是零，而代价是把随机崩溃变成了确定行为。这笔交易很划算。

`_on_com` 里那个「自己等自己」的短路不是优化，是**防死锁**：工作线程内部若再调用一个走 `_on_com` 的方法，没有这个判断就会永远等下去。

### 一个反直觉的推论

进程存活 ≠ 端点存活。桥的父进程是 `.venv\Scripts\python.exe`，它真正监听 8770 的是它拉起的**孙进程**（系统 Python）。所以父进程退出时端口可能还在服务。看护逻辑因此在重启前先**探端口**，而不是只看进程句柄的退出事件——否则会把一个健康的桥反复杀掉重启。

## 为什么用 HTTP 而不是 stdio

两种传输都能用，仓库里也都留着。**默认走 HTTP**，理由只有一个：**谁拥有进程**。

| | stdio | HTTP |
|---|---|---|
| 谁拉起桥 | `dsh-mcp-client` 自己 | 本插件 |
| 面板能否启停重启 | 不能，碰不到 | 能 |
| 崩溃后能否自动拉起 | 客户端会重连，但你看不见进程 | 看护逻辑接管 |
| 日志能否进面板 | 能（客户端转发） | 能（插件直接读管道） |

如果桥的生死不归插件管，那「重启 MCP 进程」这个按钮就没有意义。HTTP 让插件成为父进程，面板才真的可控。

代价是多了一个端口和一个「进程起来了但还没监听」的时间窗。后者用 `failOnStartupError: false` + 重连退避解决：头几次连不上是正常的，不是错误。

## 路径全部运行时解析

第一版把 `F:\DSH对CAD2024插件\...` 写死在配置里。换台机器就全废。

现在的解析顺序：

- 桥目录：`AUTOCAD_BRIDGE_DIR` 环境变量 → 包内 `bridge/` → 同级 `bridge/`（开发布局）→ 当前工作目录。**带 `.venv` 的优先**，因为从包仓库安装时源码目录可能是只读的，而已经建好的依赖更有价值。
- venv：`~/.dsh/autocad-bridge/.venv` 优先，其次源码旁的 `.venv`。写进数据目录是为了升级包时不丢依赖。
- Python：`AUTOCAD_BRIDGE_PYTHON` → venv → PATH。
- ProgID：`CAD_PROG_ID` → `AutoCAD.Application.24`，并可让面板现查注册表。

持久化的 `config.json` 会**逐字段校验后再采纳**：路径必须真实存在（`fs.statSync`），端口必须是合法整数。这样一份从别的机器带过来的配置不会把插件钉在已消失的目录上。

## 配置放在哪里，为什么

- **用户可调参数** → `~/.dsh/autocad-bridge/config.json`。放用户目录，安装包升级不会覆盖。
- **底层参数**（超时、重试、默认图层）→ 包内 `bridge/.env`。这些改的人少，跟着代码走。
- **不声明 Cordis Config schema**。宿主查询会显示 `status: "absent"`，这是刻意的：插件参数由自己的面板管理，走两套配置系统只会让人困惑该改哪边。

## 桥为什么不做视觉验证

桥能确认「这个圆画出来了、句柄是 0x81、圆心在 (210,175)、半径 40」，但它不能确认「这张图好看」。这是刻意的边界：桥负责**把意图变成实体**，好不好看是另一个环节的事（需要截图 + 看图）。

把判断塞进桥里，会让桥依赖图像模型，也就意味着没配视觉模型时桥就废了。现在没有视觉也能画图，只是没人替你看。
